# 执行结果与恢复

## 结果怎么读

普通成功输出直接是结果 JSON，没有通用 `ok:true` 信封。自动化使用 `--json`；目录树与分享地址存在默认文本输出。错误通常在 stderr 的 `error` 对象里，但 stderr 也有进度文本，不能把每行都当 JSON。

大响应先用命令已有的范围、模式、筛选与分页缩小读取；完整响应保存到任务文件，再按需选取字段，不虚构 `--fields`。工具输出被截断时补读缺失部分或明确未读范围，不能声称已加载全文。

exit 0 只说明该命令正常返回；状态查询也可能成功返回一个失败任务。将“请求已受理”“执行已完成”“内容已保存或发布”“实际作品经过检查”分开报告。批量操作按每项、多输出生成按每个输出判断；保留成功项、失败原因与未观察到的范围。

观察协议各自不同：generation 的 `task_snapshot/task`、tool 的 `run_snapshot/run`、aesthetic 的普通 run 和 Composer 的事件不能交给同一个固定解析器。观察命令的失败/部分成功/取消常用 exit 6，需要关注为 7，超时为 8，本地 Ctrl+C 为 130；资源 watch 的超时正常为 0。具体仍以该命令状态及结果为准。

## 结果不确定时

| 操作 | 恢复依据 |
| --- | --- |
| generation 提交 | 原目标、原请求与同一幂等键，或已记录 task ID。CLI 回执只保留摘要和 task 身份，不保存完整提示词/body |
| 上传、替换、目录式 tool build/publish | 原冻结字节和本地回执，按该命令 `--resume`；不改文件后声称仍是同次请求 |
| 明确 tool/artifact 的发布 | 核对同一 artifact 与范围；此形式不接受 `--resume` |
| 资源批量改动 | 先按原 key 核对原请求。已确定逐项结果后，才用新 key 只做需要重做的失败项 |
| mkdir、canvas create、Composer send | 先查现有目录/画布或 Composer get/history/watch，不能用盲目重试产生第二份对象或消息 |
| 权限变更 | 查当前规则和实际应用结果。`applied:true` 加刷新失败仍表示已写入 |
| aesthetic train | 保留原 body 与原 key；CLI 没有该流程的本地完整请求快照 |

读操作遇到 500/503，可在原范围有限重试。写操作受理结果不明时，先保留原请求和回执；已取得 task/run 等身份时优先查原结果。尚未取得身份、查询也不能确认时，若该操作有专属的同键重放或冻结恢复合同，且原请求证据完整，就按该合同找回原受理；不能换键或改输入。没有这类合同或原请求证据不足时，保留未知并停止相关写入。管理类写入按自身状态与修订核对，不套用生成或 tool run 的幂等规则。

幂等键用于恢复同一请求，不能为了绕过冲突换 key 重做整批或重复收费。`retryable` 也不是重新创建任务的授权。

观察断线、超时或本地中断时继续原 task/run/turn；停止观察不自动取消远端。资源 watch 从已处理完整页的检查点续接，不套 task/run 恢复。取消、中断或恢复已受理后，继续核对实际状态；已生成或已修改的内容不承诺回滚。

## 修订冲突

重读当前对象，与原输入及用户目标比较，合并有意保留的变化。不要只换成新 expected revision 再覆盖。改变请求内容、目标或 artifact 后，重新建立对应证据，旧测试结论不能证明新产物。
